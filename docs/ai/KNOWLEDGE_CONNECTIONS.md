# Knowledge connections and Calendar hymn recommendations

## Local implementation

`src/lib/knowledge/connections.ts` defines stable typed nodes and relationships for hymns, saints, feasts, biblical events, Scripture, themes, calendar days, Synaxarium entries, and historical topics. Every link carries evidence, confidence, editorial status, source type, and provenance. The read API returns confirmed links only. Generated and historical links remain proposed. `synaxariumConnections.ts` uses the existing multilingual entity dictionary and returns a saint candidate only when the complete title resolves uniquely.

Run `npm.cmd run build:knowledge-connections` to regenerate `artifacts/knowledge-connections/candidates.json`, the small hymn-to-passage navigation index in `src/data/knowledgeCandidatePassages.ts`, and a compact occasion/category/language source snapshot in `src/data/knowledgeHymnMetadata.ts`. The tool reads the 2,531-row original hymn CSV, the deep-classification batch, the existing calendar card and hymn exports, and reviewed/public/published Bible passage snapshots. It never calls a paid API or writes to Supabase. The current audit produced **94 proposed relationships**, including 19 surviving legacy calendar/hymn links, 50 calendar-card dates, six full-lyric primary saint proposals, seven full-lyric theme proposals, six Transfiguration event candidates, and six Matthew 17 passage candidates. It rejected **87 stale legacy links** because their hymn is absent from the current retained export. No full-verse quotation met the strict match rule; **zero direct quotations** are claimed. The Matthew connections are clear-event candidates grounded in literal Tabor and Moses words and a reviewed passage snapshot, not quotations or prescribed readings.

The old `calendarMezmursData.ts` generator sets `review_status: 'approved'` by default. That flag has no independent human-review provenance. The new layer keeps those links as *candidates* and `CONFIRMED_KNOWLEDGE_CONNECTIONS` empty until an authenticated editorial decision with evidence is available. This protects against interpreting a single saint mention or autogenerated label as a hymn's liturgical assignment.

## Runtime ranking and presentation

The existing `recommendDailyMezmurs` path remains inside the lazy day-context load. For one day it examines the small calendar link index, fetches only selected hymn slugs from `mezmur_public`, and drops missing or unpublished rows. It requests title/language/media metadata, not lyrics. The public view does not expose category or occasion, so the compact generated source snapshot supplies those labels and is only used after the live published hymn lookup succeeds. That metadata may be stale until regenerated; it is not presented as a new editorial approval. The order is: separately confirmed direct feast or saint relationship; explicitly verified occasion metadata when supplied by a compatible source; source occasion metadata with pending-review wording; unreviewed calendar candidate; general published fallback. The current public view cannot supply an occasion verification flag, so the verified-occasion tier only activates for a future compatible source or test fixture. The generic CMS `review_status` is not used as classification approval. Candidate copy never asserts a traditional prescription. The Calendar dashboard now shows a compact relevant-hymns list with category, language, applicable event, reason, and a working canonical `/hymns/mezmur/:slug` link. The expanded Calendar event panel lazy-loads only its linked published hymns and labels them as related candidates.

Hymn detail offers a clearly labeled Matthew 17 exploration link for the six event candidates. It does not call the text a quotation. Synaxarium entries with one unambiguous saint name offer a Saints-library search link. No unapproved hymn links are inserted into the Bible page as authoritative related hymns.

The date engine, timezone conversion, Ethiopian date rules, existing routes, and source lyrics/verses were not changed. The new day-to-commemoration API accepts IDs from the resolved calendar day; it does not recalculate dates.

## Checks and performance

`npm.cmd run test:knowledge-connections` validates candidate status, source provenance, stale-link rejection, saint, theme and date connections, no invented quotation, ranking tiers, missing-hymn exclusion, locale reason availability, direct navigation URLs, and empty results. A local in-memory benchmark ran 100 targeted recommendations in **about 3 ms** total on the test host. That measures ranking only, not network latency or React rendering. The existing Calendar context cache and targeted Supabase read determine live latency.

Current worktree checks passed: 17/17 Calendar–Mezmur link regressions and Bible search against configured read-only Supabase; 50/50 Ethiopian calendar engine checks including 36,890 daily round trips; Calendar card reconciliation, Synaxarium presentation, Mezmur presentation, targeted ESLint, TypeScript, and production build. A mobile Calendar browser check against a fresh local preview passed its language-switch step but could not open an event detail in this data environment (`CAL-01/02`); the event-detail flow remains unverified by that browser test. An earlier run against the already occupied port 4173 failed at the header language button, so that run was not treated as an app result. Repository-wide ESLint has pre-existing errors in unrelated files, so the changed files were linted directly.

## Editorial work still needed

The six Transfiguration and six primary-saint candidates require human confirmation before authoritative cross-page display. Those relation types remain supported by the model and empty in confirmed data. No database schema or live write was added.
