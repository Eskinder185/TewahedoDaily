# Faith Challenges: public page to CMS integration (2026-11-03)

Local code and offline fixture verification only. No SQL, migration, hosted Supabase access, production data change, staging, commit, push, merge or deployment. The existing twelve-game Visual Studio, its editors, the game mechanics, Game Night and XP code were not rebuilt or changed.

## What was wrong

`/admin/play` listed only **saved** records (browser-local drafts and server rows). Games whose content ships inside the app (static TypeScript banks) therefore looked empty, the hub's game cards, categories and ordering were not visible anywhere in the CMS, and the locally generated Bible campaign had no review surface. The public hub also kept its game metadata inline in `PlayHubPage.tsx`, so the CMS could not read the same definitions.

## What changed

1. **One shared definition of the public hub.** `src/lib/play/gameCatalog.ts` now holds the twelve game cards and the five category filters. `PlayHubPage` imports it (same data, same rendering) and the Studio reads the same module, so game metadata is defined once.
2. **Every game shows its existing content.** `src/lib/play/staticContent.ts` reads the actual public banks (`approvedContent.ts`, `bibleTimeline.ts`, `bibleAdventureStories.ts`, `imageCatalog.ts`) and the Studio lists them read-only, labelled "Live · built-in" with the true source file. Opening an item creates an independent **draft copy**: quiz copies get a fresh ID; every other format keeps its stable ID (story and image IDs name artwork and sources). Originals are never mutated and a copy never reaches the public game. Built-in counts: trivia 20 · emoji 6 · finish-the-verse 5 · history 9 (including 3 chronology events) · who-am-i 6 · match 8 · bible-timeline 5 chains · adventures 6 stories · feasts 12 · saints 10 · icon-memory 22 · finish-the-mezmur is derived from published Mezmur records.
3. **Compact mirror of the public page** (`/admin/play`): tabs Library, Game settings, Coverage, Campaign drafts. With no game selected the Library shows one 12-row table (category, built-in count, saved server/local counts, source, publishing capability) plus the five categories and five modes. Selecting a game shows its saved records followed by its built-in content, with the existing search, status, category, difficulty and language filters applied to both. The old per-game cards stay removed.
4. **Game settings** (`src/lib/play/gameSettings.ts`, panel in `StudioPanels.tsx`): bilingual title, description, short facts and instructions, thumbnail from the existing artwork catalog, display order, featured, enabled and difficulty availability, with validation (unique order, valid levels, at least one game enabled) and an **accurate preview using the real hub card component**. These are **local, unpublished proposals** scoped to the staff user. The panel says so, and a test proves the public hub does not read them.
5. **Coverage matrix** (`src/lib/play/coverage.ts`): every content-driven public feature with source, CMS view, editability, adapter and blocker, generated from code and checked by tests (every referenced source file must exist).
6. **Campaign drafts** (`src/lib/play/campaignDrafts.ts`): open `batch-00N/drafts.json` or `library/all-drafts.json`. Each generated question shows batch, book, chapter and verse, type, difficulty, English and Amharic, source evidence (passage, verse ID, edition, model, source hash), the CMS-validator result, an "Amharic unverified" tag and a separate **human review** state kept in the reviewer's browser. The only output is a download of validated **draft candidates** for the existing `/admin/play/import` tool (no status or publish field, English-only verified locales, provenance kept). Nothing is approved or published, and an invalid draft can never be exported, even if marked ready.

## Safety properties preserved

- Drafts, review, approved, rejected and archived content still cannot enter public gameplay: no public reader was changed, and none reads Studio storage, settings proposals or campaign review state.
- Unsupported formats remain blocked from publication; the Who Am I and Match publication guards are unchanged.
- Game Night, XP, rewards and the private question bank are untouched; the matrix lists Game Night as read-only on purpose.
- Editing published content still follows the locked-until-returned-to-draft rule; copies never replace published rows.

## Remaining blockers

- **No public adapter for hub settings, instructions or hub copy.** A reviewed table, RLS and reader are needed first: `docs/ai/proposed-migrations/20261104_play_game_settings_proposal.md` (proposal only, not executed).
- Eight formats still have local-only drafts and static public banks (see matrix). History chronology, adventures, timelines and image games need server schemas and readers. Artwork upload remains the existing media workflow.
- Live six-state constraints, grants and RLS remain unverified until separately authorized isolated staging.
- Generated Amharic needs native-speaker review before any locale is marked verified; the campaign panel never does this.
- Local settings and review decisions are per browser and per staff user; they do not synchronize across devices.
