# Mezmur save and publishing 42501 diagnostic — 2026-10-24

> Historical diagnostic: the separate approval workflow described below is
> superseded by `mezmur-two-status-publication-workflow-2026-10-24.md` and the
> forward migration `20261024150000_mezmur_publish_without_editorial_review.sql`.

## Root cause in the application

The quoted error was not the original PostgreSQL error. It was generated by
`mapStaffWriteError()` in `src/lib/cms/cmsStaffAuth.ts`. That function replaced
every SQLSTATE `42501` from several different operations with the same advice to
run `FIX_ZEMARI_STAFF_WRITE.sql`. Consequently the UI could not identify the
failing table, RPC, trigger, RLS policy, sequence, database detail, or hint.

The operations that could produce that identical message were:

- `PATCH public.mezmur_data_import` by `mezmur_id`
- its fallback `PATCH public.mezmur_data_import` by slug
- `POST public.mezmur_data_import`
- `RPC public.publish_mezmur_import`
- `PATCH` or `POST public.zemaris`
- the follow-up Zemari link update on `public.mezmur_data_import`

This information loss is why the historic message alone cannot prove which one
failed. The local fix now prefixes the exact operation and preserves Supabase's
`code`, `message`, `details`, and `hint`. It also recognizes the two guarded
trigger errors and names `public.mezmur_data_import_publication_guard` plus the
required RPC.

## Publication guard and ordinary Save payload

The repository defines one trigger on the active Mezmur table:
`mezmur_data_import_publication_guard`, a `BEFORE INSERT OR UPDATE` trigger that
calls `public.guard_mezmur_import_publication()`.

It intentionally raises `42501` when either:

1. an update directly transitions `status` to `published` instead of using
   `public.publish_mezmur_import()`, or
2. an ordinary insert/update changes `review_status`, `rights_status`,
   `publication_approved_at`, or `publication_approved_by` instead of using
   `public.approve_mezmur_import()`.

The current ordinary editor payload is explicitly constructed from content
fields and does **not** contain any of those four protected approval fields. A
new local assertion rejects a future regression before it reaches Supabase.
When Publish is requested, the ordinary update retains the prior status and the
separate guarded publication RPC performs the transition.

Therefore a protected-approval-field rejection is not caused by the current
local payload. A deployed older client that sends `status = 'published'`
directly will be rejected by the trigger with the first `42501`; deployment was
not performed as part of this work.

## Authenticated identity verification

Previously the save preflight trusted the cached session user and called only
`public.is_staff()`. It did not prove that the access token validated to the same
user as the cached session or show which `profiles` row supplied the role.

The local preflight now, immediately before a write:

1. reads the cached session and reapplies its token to the client;
2. calls `auth.getUser()` to validate the JWT with Supabase Auth;
3. selects the caller's own `public.profiles(id, role)` row;
4. requires the session user ID, validated JWT user ID, and profile ID to match;
5. requires the profile role to be `editor`, `admin`, or `super_admin`; and
6. requires `public.is_staff()` to return `true` under that same JWT.

The repository/anonymous environment cannot impersonate the administrator's
browser session, so it cannot truthfully report that user's runtime UUID. On the
next local save the UI will now distinguish a stale JWT, missing/mismatched
profile, non-staff role, `is_staff()` disagreement, or the subsequent database
write. No role or production profile was changed.

## Additional database causes covered

`supabase/mezmur-import/DIAGNOSE_MEZMUR_42501_READ_ONLY.sql` inventories, without
mutation:

- every non-internal trigger and its complete function definition on the save
  tables;
- RLS state and policies;
- authenticated table and payload-column privileges;
- foreign keys and referenced tables;
- defaults, owned sequences, and sequence `USAGE` privileges; and
- ownership/security-definer/EXECUTE state for `is_staff`, approval,
  publication, and guard functions.

This is needed because production may have triggers that are not represented in
the repository. Running it in SQL Editor inventories schema state, but SQL
Editor normally has no browser JWT (`auth.uid()` is null); the application
preflight is the authoritative per-session check.

## Active table and public visibility

The current admin editor reads `public.mezmur_data_import`; setting status in a
different table is irrelevant. The proposed public frontend reads the narrow
`public.mezmur_public` projection, which requires published status, approved
review, allowed rights, and recorded approval metadata, and fully paginates.
Earlier read-only production observations found 1,153 import rows: 265 marked
published and 888 draft, but zero with `review_status = 'approved'`; the queried
production schema also lacked `rights_status`. Those rows must not be silently
force-published or treated as rights-approved.

## Local fixes and regression coverage

- Precise operation-aware PostgreSQL/PostgREST errors replace the generic 42501.
- JWT user, profile identity/role, and `is_staff()` are cross-checked per save.
- Ordinary save payloads are prevented from including approval-owned fields.
- Publication transitions use `public.publish_mezmur_import()`.
- Admins and super admins now have a separate approval panel and action that
  calls `public.approve_mezmur_import()` only after an explicit source, lyrics,
  and rights attestation. Editors can see the approval state but cannot approve.
- The editor reloads the row after approval and enables the separate Publish
  action only when the database confirms review, rights, approver, approval
  time, and required content fields.
- Regression tests cover authorized `super_admin`, stale-session mismatch,
  non-staff denial, `is_staff()` disagreement, all four protected fields,
  trigger-specific 42501 diagnostics, RLS/table and sequence errors, and the
  read-only diagnostic script.
- A mocked Playwright test covers Save Draft → super-admin Approve → Publish,
  verifies ordinary saves omit all protected fields, and verifies editors do
  not receive an approval action.
